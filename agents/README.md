# QA-персонажи

Персонажи ходят по тестовому стенду как пользователи, по ходу с их устройством случаются события среды, и каждый пишет отчёт о том, что увидел. Задача: belousovsn/Translator-app#747.

## Из чего состоит

| Файл | Что в нём |
|---|---|
| `personas/*.md` | персонажи: кто, характер, цели; в шапке устройство, язык, тема, аккаунт |
| `rules.md` | правила, по которым персонаж судит |
| `accepted.md` | находки, признанные нормой |
| `lib/events.mjs` | события среды и их случайный выбор по зерну |
| `lib/prompt.mjs` | задание персонажу и формат отчёта |
| `lib/claude.mjs` | запуск `claude -p`, проба лимита, решение «запускать, ждать, пропустить» |
| `lib/verify.mjs` | проверяющий: вердикт по каждой находке по снимкам и журналу |
| `lib/triage.mjs` | разборщик: по доске решает, какие находки станут задачами |
| `lib/knowledge.mjs` | решения по находкам и клиент GitHub |
| `lib/planner.mjs` | режим по дифу: очередь деплоев, планировщик, фокус для персонажа |
| `enqueue.sh` | принудительная команда ключа деплоя: кладёт дифф в очередь и будит раннер |
| `lib/game-mock.mjs` | мок игр: подставная страница вместо игры и способы выйти из игры |
| `server.mjs` | API страницы: ручной запуск и состояние раннера (служба `qa-agents-api`) |
| `lib/site.mjs` | страница с двумя последними прогонами каждого персонажа |
| `run.mjs` | запускалка |
| `run.sh` | вход на droplet-b: блокировка от параллельных запусков и настройки из `/etc/qa-agents.env` |

Персонажи с `account: guest` запускаются уже сейчас. Остальным нужны тестовые аккаунты.

## Как идёт прогон

1. Проба лимита: короткий вызов Haiku, из события `rate_limit_event` берутся загрузка и время сброса. Меньше 50% занято: запуск. Больше: ожидание сброса. Сброс дальше шести часов (недельный лимит): пропуск с сообщением в Telegram.
2. Персонажи идут по одному. У каждого свой вызов Claude (`claude-sonnet-5-5`), свой браузер через Playwright MCP с эмуляцией устройства, свой план событий среды.
3. В папке прогона остаются отчёт, скриншоты находок, трейс (`trace.zip`), журнал вызовов браузера и поток Claude. Хранятся два последних прогона на персонажа.
4. Проверяющий (`claude-opus-5-5`, без браузера) читает отчёт рядом со снимками экрана, снимками страницы и журналом действий (`timeline.md`). Каждой находке он ставит вердикт: подтверждено, переформулировано, отклонено, не проверить. Ещё он добавляет явные нарушения, которые персонаж пропустил. Результат лежит в `verify.json`.
5. Разборщик решает по доске, что из находок станет задачей (см. ниже).
6. Страница пересобирается. В Telegram уходят только подтверждённые и переформулированные находки, у каждой экран, где она случилась, и ссылка на неё на странице. Ниже идёт итог разбора: новые задачи со ссылками и уже заведённые.

## Разбор по доске

После всех персонажей одного прогона запускается разборщик (`claude-opus-5-5`, без браузера). Он получает находки, которые прошли проверку и ещё не решены, и доску: открытые задачи `belousovsn/Translator-app`, закрытые за 90 дней и колонку каждой задачи на доске. По каждой находке он решает одно из трёх:

- **новая задача**: проблема настоящая, и на доске её нет. Задачу заводит раннер, в описании что не так, что должно быть, где и все случаи со ссылками на страницу;
- **уже есть #N**: на доске есть задача про то же. Если она в колонке «On test», а на стенде проблема всё ещё видна, это отдельно отмечено в Telegram;
- **не заводить**: так задумано, проблему вызвало само тестирование, или находка слишком расплывчатая.

Одинаковые находки разных персонажей становятся одним решением. Новых задач за разбор не больше пяти. Решения пишутся в `knowledge.json` с пометкой «разборщик» и причиной. Заведённые задачи персонажи дальше считают известными. «Не заводить» персонажам не показывается, а на странице у такой находки остаются кнопки: можно завести задачу самому. Перед отправкой из заголовка и описания вырезаются пароли тестовых аккаунтов и всё, что похоже на токен. Папка разбора `triage/<время>/` с доской, заданием и ответом хранится для десяти последних разборов.

Разобрать последние прогоны заново, не проходя сайт: `run.sh --retriage hy-veteran guest-then-signin`. Без разбора: `--no-triage`.

## Игры

В каждом прогоне по зерну выпадает, какие игры: мок (60%) или настоящие, и какими способами из них выйти: доиграть, выйти раньше, обновить страницу посреди игры. В моке агент подменяет адреса всех игр подставной страницей (`mock-games.js` в папке прогона). Она проходит рукопожатие с приложением, показывает, что пришло (карточки, языки, токен, ответ `/api/cards`), и отправляет ответы на карточки, результат или закрытие. Так проверяется приложение вокруг игр, а сами игры не трогаются. Проверка мока в браузере: `node test/game-mock.browser.mjs`.

## Ручной запуск

На странице у каждого гостя есть кнопка «Запустить», наверху «Запустить всех гостей» и строка с тем, что идёт сейчас. Кнопки ставят задачу в ту же очередь, что и деплои, ручные идут первыми. API живёт на `127.0.0.1:8791` за тем же паролем, что и страница (`/agents/api/`); запуск требует заголовок `x-qa-agents: 1`, его не подделать формой с чужого сайта.

## После деплоя на тест

1. Задача `qa-agents` в `deploy-test.yml` после зелёного деплоя собирает коммиты и дифф между прошлым и новым `dev`. Дифф идёт по ssh на droplet-b под пользователем `qa-agents`. Ключу разрешена только команда `enqueue.sh`, деплой ответа не ждёт.
2. `enqueue.sh` кладёт дифф в `/var/lib/qa-agents/queue` и запускает `run.sh --from-queue`. Если раннер занят, задачу подберёт он же, когда закончит, или крон раз в 15 минут.
3. Несколько деплоев подряд склеиваются в один прогон. Планировщик (`claude-opus-5-5`) решает, видно ли изменение пользователю. Если не видно, прогона нет. Если видно, он выбирает до двух персонажей и места, куда им сходить по ходу своих целей.
4. Дальше всё как в обычном прогоне: проверяющий, страница, Telegram. В сводке и на странице видно, после какого деплоя был прогон и что поменялось.

## Запуск

На droplet-b:

```bash
sudo -u qa-agents /opt/qa-agents/agents/run.sh guest-ru-phone
```

Проверить последний прогон заново, не проходя сайт: `run.sh --reverify guest-ru-phone`. Флаги: `--no-verify`, `--no-triage`, `--no-notify`, `--no-probe`, `--seed=N`, `--max-actions=N`.

Локально, без подписки, с заглушкой вместо Claude можно проверить всё, кроме самого агента: `CLAUDE_BIN=<путь к .mjs>` запускает этот файл вместо `claude`.

```bash
cd agents && npm ci --ignore-scripts && npx playwright install chromium
npm run check
```

## Настройки (`/etc/qa-agents.env`)

| Переменная | Значение |
|---|---|
| `CLAUDE_CODE_OAUTH_TOKEN` | токен подписки из `claude setup-token` |
| `TEST_BASE_URL` | адрес стенда |
| `QA_AGENTS_HOME` | папка с прогонами и страницей |
| `QA_AGENTS_PAGE_URL` | адрес страницы для ссылки в Telegram |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | бот дайджеста |
| `QA_AGENTS_PERSONA_MODEL`, `QA_AGENTS_PROBE_MODEL`, `QA_AGENTS_VERIFY_MODEL`, `QA_AGENTS_PLANNER_MODEL`, `QA_AGENTS_TRIAGE_MODEL` | замена моделей, по умолчанию `claude-sonnet-5-5`, `claude-haiku-5-5` и `claude-opus-5-5` для остальных |
| `QA_AGENTS_GITHUB_TOKEN`, `QA_AGENTS_GITHUB_REPO` | токен с правом на задачи и репозиторий, куда они заводятся |
| `QA_AGENTS_BOARD` | доска как `владелец/номер`, по умолчанию `belousovsn/2`; без доступа к ней разборщик видит задачи без колонок |
| `QA_AGENTS_QUEUE` | папка очереди деплоев, по умолчанию `/var/lib/qa-agents/queue` |
